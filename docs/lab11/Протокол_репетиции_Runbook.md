# Репетиция Runbook TourFlow

**Дата репетиции:** 10.11.2026  
**Формат:** tabletop-разбор (учебный сценарий без создания реального сбоя)  
**Система:** https://tour-request-system.onrender.com/  
**Роли:** QA/DevOps — обнаружение и первичная диагностика; Backend — оценка совместимости и данных; PM/BA — уведомление и журналирование.

## Сценарий

Предположим, после нового деплоя стенд открывается, но вход или создание заявок перестали работать. Это условный сценарий, не фактический инцидент.

## Ход репетиции и ожидаемые действия

| Этап | Действие по Runbook | Результат tabletop-разбора |
|---|---|---|
| Обнаружение | Зафиксировать URL, время, ошибку, SHA деплоя и логи Render | Команда знает, какие сведения записать; фактический SHA текущего Render-деплоя в рамках репетиции не извлекался |
| Сдерживание | Уведомить PM/BA и команду, приостановить релиз и новые тестовые записи | Принято как первый шаг; реальные пользователи/данные не затрагивались |
| Решение | Проверить последний известный исправный SHA и совместимость схемы SQLite | Для критического отказа входа/создания заявок решение об откате принимает QA/DevOps по плану ЛЗ10 |
| Восстановление | В Render выбрать предыдущий исправный деплой либо сделать revert через отдельный PR | Шаги понятны, но реальный rollback не выполнялся: активный стенд работает, намеренно ломать его небезопасно |
| Проверка | После Live проверить вход, создание, поиск, смену статуса, данные и логи | Основные пользовательские проверки на текущем стенде ранее прошли; постдеплойная проверка после отката не имитировалась |
| Закрытие | Записать incident ID, длительность, результат и действия в бэклог; провести blameless review | Подтверждено, какие поля следует внести; реальный инцидент не создавался |

## Связь с результатами UAT

Сортировка не является причиной для инцидента или отката: по предоставленным скриншотам пользователя все три режима показывают ожидаемый порядок — «Сначала новые», «Сначала старые» и «По бюджету ↓». Ранее возникшее подозрение на дефект было ошибочной интерпретацией порядка записей и исправлено после повторной сверки доказательств.

## Наблюдение Uptime Kuma от 10.11.2026

На снимке монитора TourFlow Production текущий статус указан как «Доступен». В истории есть одна запись `Request failed with status code 503` с отметкой 2026-11-10 12:17:42. По одному снимку нельзя определить длительность ответа 503, первопричину или влияние на пользователей.

Дополнительно сверены снимки Render Application Logs и Events. В логах показаны остановка и последующий запуск сервиса, а затем успешные ответы приложения; видимый `401` для `/api/me` без сессии и `404` для `favicon.ico` не объясняют ответ 503. Events показывает успешные деплои, но это журнал деплоев, а не HTTP-запросов. Прямой корреляции события Uptime Kuma с Render не найдено. Поэтому 503 фиксируется как несопоставленный сигнал мониторинга, не как подтверждённый инцидент; его причину нельзя уверенно связать ни с Render, ни с холодным запуском. При повторении следует сохранить точное время и URL монитора, проверить логи приложения и события сервиса за тот же интервал, затем действовать по Runbook.

## Вывод

Runbook прошёл tabletop-репетицию: последовательность реагирования, роли и критерии отката разобраны. Реальный инцидент и rollback не выполнялись. Для эксплуатационной готовности команда должна извлечь текущий SHA Render, проверить доступ к предыдущему deploy и отдельно отрепетировать rollback в безопасной тестовой среде.
