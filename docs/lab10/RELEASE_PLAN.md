# План релизов и отката — Tour Request System (ЛР №10)

## Что считается релизом и развёртыванием

- **Релиз**: версия с тегом `vX.Y.Z`, release notes, прошедшая CI.
- **Развёртывание на стенд**: Render перевёл сервис в `Live`, доступна главная страница по HTTPS и ручной smoke test выполнен.
- **Неудачное изменение**: после публикации возник подтверждённый пользовательский дефект, который потребовал исправления, отката или восстановления; заносится в журнал инцидентов.

## Регламент

| Этап | Владелец (роль) | Действие / доказательство |
|---|---|---|
| Планирование | PM/BA | Утверждает объём, критерии приёмки, дату окна и уведомление заказчику |
| Подготовка | Backend + Frontend | Отдельная ветка → Pull Request, описания изменений |
| Проверка | QA/DevOps | API tests, JS syntax, smoke tests, review, зелёный CI |
| Одобрение | Второй участник с Write | `Approve` на PR, не автор изменения |
| Выпуск | QA/DevOps | Merge после CI, tag, запуск деплоя Render, контроль `Live` |
| Приёмка | PM/BA + QA | Проверка входа, создания заявки, поиска, смены статуса |
| Мониторинг | QA/DevOps | Логи Render, ошибки, запись в deployments.csv |
| Откат | **QA/DevOps принимает решение единолично** | Перевод сервиса на предыдущую исправную версию, запись в incidents.csv |

## Релизные окна

План: **вторник и четверг, 15:00–16:00 (Asia/Almaty, GMT+5)**. Не в часы пик туристического агентства, не перед выходными. Для учебного проекта согласовать с заказчиком, что это действительно низкая нагрузка.

Обновления клиента: PM/BA сообщает за рабочий день до релиза: состав изменений, окно, возможные риски и план отката. После публикации: URL, версия, статус тестов и известные ограничения.

## Чек-лист релиза

- [ ] Есть ссылка на задачу/PR, одобрение и зелёный `test`.
- [ ] Тестовая база без реальных персональных данных.
- [ ] Облако настроено через secrets; в репозитории нет паролей.
- [ ] Запланировано окно и согласован ответственный.
- [ ] Зафиксированы предыдущие исправный commit SHA и URL.
- [ ] Render показал `Live`; smoke-тест входа, создания заявки, поиска, смены статуса пройден.
- [ ] Зафиксированы SHA, `Live` timestamp, duration, результат и ссылка на логи.
- [ ] Заказчик получил уведомление об окончании релиза.

## Чек-лист отката

1. **Решение принимает QA/DevOps без дополнительного согласования**, если сломаны вход, создание заявки, сохранение данных или есть критическая ошибка безопасности.
2. Зафиксировать время обнаружения и создать incident ID, уведомить PM/BA.
3. Проверить, что предыдущий commit/tag был исправным, а совместимость с БД сохранена.
4. В Render → Deploys выбрать последний исправный деплой и применить доступную операцию повторного развёртывания, **или** откатить код через отдельный revert PR с аварийным согласованным порядком и запустить новый деплой. Не подменять откат истории `git push --force`.
5. После `Live` проверить логин, создание/поиск/изменение статуса и отсутствие потери данных.
6. В `incidents.csv` записать время восстановления и **часы труда на исправление**. Провести краткий postmortem и уведомить заказчика.

**Риск:** бесплатный Render не обеспечивает постоянный диск. SQLite без внешней БД может потерять данные при пересоздании контейнера. Поэтому схема годится для учебного стенда, но не для реальных клиентов или обещаний о восстановлении данных.

## Два измеримых улучшения

| Улучшение | Владелец | Ожидаемый эффект (план, не факт) | Дата пересчёта |
|---|---|---|---|
| Автоматический smoke-test после каждого `Live` и журнал Deploys/Incidents | QA/DevOps | Проверка входа/создания заявки ≤ 3 мин после релиза; 100% деплоев с записанным результатом и SHA | 17.11.2026 |

## Уровень DORA и capacity

Сейчас **уровень неопределён** по каждой метрике из-за одной подтверждённой публикации и отсутствия завершённого журнала инцидентов. При накоплении ≥ 4 недель наблюдений сравнить по выбранной опубликованной шкале DORA (с годом методики). Не назначать уровень вручную по одной точке.

На текущих подтверждённых данных **зарегистрированные часы исправлений после неудачных развёртываний = 0 ч**, но это не доказательство отсутствия всех дефектов. Предложение для capacity: выделить **15%** от 40 командных часов в неделю = **6 часов/неделю** на наблюдаемость, тесты, безопасность и восстановление. Это плановая квота, а не статистически выведенное значение. Через 4 недели пересчитать её по фактическим часам `incidents.csv`.
