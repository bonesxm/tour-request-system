ADR-001: Выбор модели поставки проекта

Статус: Принято
Дата: 22.09.2026

КОНТЕКСТ

Команда разрабатывает веб-систему управления заявками клиентов туристического агентства. Сейчас заявки клиентов поступают через разные каналы: WhatsApp, Instagram, телефон и другие источники. Информация о клиентах и состоянии заявок может оставаться в переписках, поэтому менеджеру приходится вручную контролировать этапы обработки заявок.

Основные функции системы определены заранее: создание и редактирование заявки, хранение данных клиента, указание направления, дат поездки и бюджета, назначение ответственного менеджера, изменение статуса заявки, поиск, фильтрация и просмотр истории изменений.

При этом отдельные требования могут уточняться в процессе общения с представителем туристического агентства. Поэтому необходимо выбрать модель поставки, которая позволит сохранить общий план проекта и одновременно учитывать изменения требований.

ДВИЖУЩИЕ СИЛЫ

1. Основная часть требований известна заранее.
2. Некоторые требования могут изменяться после обратной связи заказчика.
3. Проект выполняется небольшой командой из четырёх человек.
4. Срок разработки ограничен учебным семестром.
5. Необходимо регулярно получать промежуточные результаты.
6. Ошибки желательно обнаруживать до завершения всей разработки.
7. Заказчик может иметь ограниченное время для регулярного взаимодействия с командой.

РАССМОТРЕННЫЕ ВАРИАНТЫ

Вариант 1. Waterfall

Разработка выполняется последовательно: определение требований, проектирование, разработка, тестирование и завершение проекта.

Преимущество: понятная последовательность этапов и возможность заранее составить общий план проекта.

Недостаток: изменение требований после начала разработки может привести к необходимости переделывать уже выполненную работу.


Вариант 2. Scrum

Разработка выполняется короткими итерациями. После каждой итерации команда получает промежуточный результат и может корректировать дальнейшие задачи.

Преимущество: возможность быстро учитывать изменения требований и обратную связь заказчика.

Недостаток: требуется регулярное взаимодействие с заказчиком и постоянное управление списком задач.


Вариант 3. Гибридная модель

Основные цели, границы и ключевые функции проекта определяются заранее, а непосредственная разработка выполняется небольшими итерациями.

Преимущество: модель сочетает предварительное планирование с возможностью корректировать отдельные требования во время разработки.

Недостаток: необходимо контролировать изменения, чтобы они не приводили к постоянному расширению границ проекта.


РЕШЕНИЕ

Для проекта выбрана гибридная модель поставки.

Основные требования, границы проекта и ключевые функции системы фиксируются заранее. Разработка выполняется небольшими итерациями.

Задачи создаются и отслеживаются через GitHub Issues и GitHub Projects. После реализации отдельных функций команда проводит их проверку и при необходимости уточняет следующие задачи.

Такая модель позволяет сохранить общий план проекта и одновременно учитывать обратную связь представителя туристического агентства.


ПОЛОЖИТЕЛЬНЫЕ ПОСЛЕДСТВИЯ

1. Команда регулярно получает промежуточный результат.
2. Требования можно уточнять во время разработки.
3. Ошибки можно обнаруживать на ранних этапах.
4. Задачи между участниками команды распределяются прозрачно.
5. Состояние проекта можно контролировать через GitHub Projects.
6. Снижается риск большой переделки системы в конце проекта.


ОТРИЦАТЕЛЬНЫЕ ПОСЛЕДСТВИЯ

1. Необходимо регулярно обновлять список и статусы задач.
2. Требуется дополнительное время на управление задачами.
3. Все изменения требований необходимо фиксировать.
4. Существует риск постепенного расширения границ проекта.
5. Ограниченная доступность заказчика может задерживать подтверждение отдельных требований.


КРИТЕРИЙ ПЕРЕСМОТРА

Выбранная модель поставки должна быть пересмотрена в следующих случаях:

1. Заказчик перестанет регулярно предоставлять обратную связь.
2. Требования к системе станут полностью фиксированными и дальнейшие изменения не будут ожидаться.
3. Количество изменений требований начнёт существенно влиять на сроки выполнения проекта.
4. Выбранный процесс перестанет позволять команде выполнять задачи в соответствии с учебным графиком.

Если возникает одно из этих условий, команда повторно рассматривает модель поставки и фиксирует новое решение в отдельном ADR.
